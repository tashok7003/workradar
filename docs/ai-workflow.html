02Significant prompts

a. Build prompts (to Claude)

The brief went in as six messages, one per requirement block (context, PRD, UX design, working MVP, AI workflow, final deliverables), with an explicit "don't start until I say start". Claude summarised each block, flagged open decisions (stack, live vs. pre-generated AI, design tool, repo vs. ZIP), and on "start" chose defaults and logged them here. Representative steering lines from the build:

"Mock data is acceptable" → model one realistic team (7 people, 27 items across Jira, GitHub, Slack, email) with connected stories, e.g. an incident whose fix PR waits on review while the customer's CTO emails for an ETA.
"AI-generated summary" must be real AI where possible, but must never break for a reviewer without an API key → provider chain: Claude in the hosted demo → Claude via local API key → labelled rules-based fallback.
Ranking must be explainable → "rules rank, AI explains": deterministic scores with visible reasons; the model only summarises the ranked list and every item it cites must exist.

b. Runtime prompt: daily briefing (abridged from briefingPrompt())

You are WorkRadar, a chief-of-staff assistant for an engineering manager. Write today's briefing from the work items below. They come from Jira, GitHub, Slack and email and are already ranked by urgency.
Rules: Use only facts in the data. Do not invent people, numbers, times or causes. Address the manager as "you". Each line is one sentence, at most 24 words, and names the concrete next step. Cite the item ids each line is about, using only ids from the data. When several items are one situation, cover them in one line. "blocked": lead with anything blocked on the manager.
Reply with only this JSON: {headline, attention[2-3], blocked[≤4], happened[≤3], suggestion} … DATA: {…}

c. Runtime prompt: reply or nudge for one item (abridged from nudgePrompt())

Draft Ashok's reply to {sender} (2-4 sentences, plain and direct, no emoji). Acknowledge the ask and commit to a concrete next step. Do not promise dates or facts that are not in the data; where a fact is unknown, say Ashok will confirm it and when.   [Blocked items instead get: "a short Slack message … to move this work forward."]

03What AI generated

  • Product: requirement breakdown, PRD content (problem, personas, journey, metrics, scope, assumptions, feature split), this document.
  • Data: the mock workspace in src/data/mock.ts, with timestamps relative to load time so the demo always reads as "today".
  • Logic: priority scoring and tiers, weighted cross-source search with highlighting, the state store (assign, done, snooze, undo, persistence).
  • AI layer: both runtime prompts, JSON parsing, citation validation, the rules-based fallback writer, provider detection, the dev-server proxy that keeps the API key off the client.
  • UI: all screens, components, styles (light and dark), empty and error states, demo controls.
  • Quality: 12 unit tests; scripted browser runs that click every action and capture screenshots.
  • Design: six artboards on the Claude design canvas, linked as a clickable prototype.

05Key trade-offs

DecisionWhyCost accepted
Rules rank, AI explainsOrder is stable, testable and explainable point by point; managers can see why something is on top.Rules miss nuance a model might catch (e.g. tone of an angry email). Weights need tuning per team.
Validate every AI citationDrops any item id the model invents, so links in the briefing always open a real item.Prose itself can't be fully verified; the prompt restricts it to supplied facts.
Three AI providers with a labelled fallbackReviewers always see a working briefing, with or without a key; the UI never calls the fallback "AI".Two code paths to maintain; the fallback reads more mechanically.
Mock data, no integrationsLets the MVP prove the experience in days, with realistic linked stories.Skips the hardest real problems: OAuth scopes, identity mapping across tools, rate limits, detecting blockers from free text.
One briefing call per change, debounced and cached 10 minKeeps the briefing current after Assign / Done / Snooze without a call per click.A briefing can trail the latest action by under a second; repeat views reuse a cached answer.
Client-only state, in-memory routingNo backend; works inside the sandboxed hosted demo.Actions don't sync across devices; no shareable deep links.
